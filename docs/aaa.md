# 프로젝트 평가 항목 답변

현재 코드와 기존 테스트를 기준으로 정리했습니다. **보완 필요**는 아직 구현하거나 검증하지 않은 부분입니다.

## 1. 로그인·로그아웃 및 세션 관리

로그인 성공 시 기존 세션을 비우고 `user_id`를 저장하며, 로그아웃 시 `request.session.clear()`로 제거합니다. 로그인 사용자가 로그인·회원가입 화면에 접근하면 `/app`으로 이동합니다. 세션 쿠키의 만료 설정은 12시간이며 만료 후 보호 경로에 접근하면 다시 로그인해야 합니다.

## 2. 비로그인 사용자 접근 제어

`require_user`가 로그인 여부를 확인하고, 비로그인 브라우저 요청은 `303` 응답으로 `/login`에 보냅니다. JSON 요청에는 `401`과 “로그인이 필요합니다.”를 반환합니다.

## 3. 보호 경로 및 직접 URL 접근 차단

`/app` 조회와 도서 등록·대여·반납 라우트 모두 `Depends(require_user)`를 사용합니다. 따라서 URL 직접 입력이나 직접 POST 요청도 인증 검사 대상이며, 비로그인 조회·변경 요청을 차단하는 HTTP 테스트가 있습니다. 버튼 숨김뿐 아니라 서버에서 검사합니다.

## 4. 사용자 상태별 UI 분기

비로그인 상태에는 로그인·회원가입 메뉴를, 로그인 상태에는 사용자 이름·대여 관리·로그아웃을 표시합니다. 대여 가능한 도서에는 대여 버튼을, 대여 중인 도서에는 대여자 정보를 표시하며, 내 기록은 대여 중일 때만 반납 버튼을 보여 줍니다. HTTP 테스트에서 로그인 전후 화면과 대여 가능·대여 중·반납 완료 문구를 확인합니다.

## 5. 도메인 모델 및 연관 데이터 구현

`User`, `Book`, `Loan`을 각각 별도 테이블에 매핑했습니다. `Loan.user_id`와 `Loan.book_id`로 사용자와 도서를 연결하고, 화면에서 `loan.book.title`, 대여자의 `display_name`, 도서별 누적 대여 기록을 출력합니다.

## 6. 대여·반납 상태 전이 관리

대여 시 `borrowed` 상태와 `borrowed_at`을 저장하고, 반납 시 `returned` 상태와 `returned_at`을 함께 저장합니다. 성공하면 `/app`으로 이동해 변경된 화면을 조회합니다. 중복 대여·타인 반납·반복 반납은 저장 전에 차단하며, 실패 후 기존 대여 상태가 유지되는 테스트가 있습니다.
**보완 필요:** 시각 값 자체와 DB 저장 실패 후 복구를 검증하는 테스트는 없습니다.

## 7. 프로젝트 실행 및 테스트 환경 문서화

[README](../README.md)에 `uv sync --frozen`, 환경 변수 설정, 실행·테스트 명령과 접근 경로 정책을 설명했습니다. 로컬 개발용 계정은 `demo / demo1234`이며, 운영 모드에서는 데모 계정을 만들지 않아 직접 회원가입합니다. 테스트는 매번 임시 SQLite DB를 사용합니다. 개발 데이터를 새로 시작하려면 `LIBRARY_DATABASE_URL`을 새 SQLite 파일 경로로 바꾸고 재실행하면 초기 데이터가 생성됩니다.

## 8. 계층별 책임 분리 및 모듈화

라우터는 요청·응답, 인증 의존성은 현재 사용자 확인, 서비스는 업무 규칙, 저장소는 DB 조회·저장, 모델은 테이블·관계를 담당합니다. 예를 들어 라우터가 `library_service.borrow_book()`을 호출하면 서비스가 조건을 확인하고 `loan_repository.create_loan()`으로 저장합니다.

## 9. 데이터베이스 연관관계 설계

`User 1:N Loan`, `Book 1:N Loan`으로 사용자와 도서의 다대다 관계를 표현했습니다. 대여 관계 자체에 상태와 대여·반납 시각이 필요해 단순 연결 테이블 대신 `Loan`을 중개 엔티티로 사용했습니다. `relationship(back_populates=...)`로 사용자·도서에서 이력을, 이력에서 사용자·도서를 탐색하고 객체 간 관계 변경을 서로 반영합니다.

## 10. 비즈니스 로직과 데이터 저장 책임 분리

서비스에서 입력값·도서 존재·대여 가능 여부·반납 소유권·현재 상태를 검사합니다. 저장소는 `select`, `add`, 상태 필드 변경, `commit`, `refresh`를 담당합니다. 따라서 업무 규칙은 서비스에서 판단하고, SQLAlchemy를 이용한 저장 절차는 저장소에서 처리합니다.

## 11. 연관 데이터 삭제 정책 및 검증

`User.loans`와 `Book.loans`에 `cascade="all, delete-orphan"`을 설정했습니다. 사용자나 도서가 없어지면 그 대상의 대여 이력도 남기지 않는 정책입니다. ORM으로 부모를 삭제할 때 해당 `Loan`은 삭제되고 반대편 사용자·도서는 유지되는 테스트가 있습니다. 이 정책은 ORM 삭제 기준이며 직접 SQL 삭제까지 보장하는 DB의 `ON DELETE CASCADE` 설정은 아닙니다. [SQLAlchemy 설명](https://docs.sqlalchemy.org/en/20/orm/cascades.html)

## 12. 의존성 주입 기반 인증 구조 이해

FastAPI가 `get_db → get_optional_user → require_user` 의존성을 실행해 DB 연결과 현재 사용자를 라우터에 전달합니다. 미들웨어가 쿠키 서명을 검증한 뒤, 인증 의존성은 `user_id`의 타입과 DB 사용자 존재를 확인합니다. 로그인 여부와 별개로 반납 서비스는 `loan.user_id == user.id`도 검사해 타인의 기록 변경을 막습니다.

## 13. 접근 제어 구현 방식 비교

의존성 주입은 라우트별 요구 조건이 명확하고 사용자 객체를 바로 전달할 수 있지만, 새 보호 라우트에서 선언을 빠뜨리지 않아야 합니다. 미들웨어는 모든 요청에 공통 정책을 적용하기 좋지만 공개 경로 예외와 경로별 권한 처리가 복잡해질 수 있습니다. 이 프로젝트는 접근 제어에 `Depends(require_user)`, 쿠키 처리에 `SessionMiddleware`, 다른 출처의 폼 요청 제한에 `SameOriginMiddleware`를 사용합니다.

## 14. ORM 기반 객체·관계 매핑 이해

SQLAlchemy의 `mapped_column`으로 열·기본키·외래키를, `relationship`으로 객체 간 관계를 정의합니다. 조회 시 `selectinload`로 필요한 연관 데이터를 묶어 읽어 반복적인 추가 조회를 줄입니다. 화면은 ORM 객체에서 필요한 속성만 읽으며, JSON API를 만들 때는 비밀번호 해시 노출·순환참조·DB 세션 종료 후 지연 조회를 피하도록 별도 응답 모델이 필요합니다.

## 15. 트랜잭션 및 데이터 무결성 관리

현재 저장소 함수별 `commit()`이 저장 경계이며, 반납의 상태와 시각은 같은 커밋으로 저장됩니다. 회원가입의 중복 아이디 `IntegrityError`는 `rollback()`하고, 요청 종료 시 DB 세션을 닫아 미커밋 작업을 정리합니다. [SQLAlchemy 설명](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
**보완 필요:** 여러 저장소 호출을 하나로 묶는 서비스 단위 트랜잭션과 공통 실패 처리는 없습니다. 중복 대여 검사도 동시 요청 사이에 경합할 수 있어, 활성 대여의 DB 제약이나 원자적 처리 및 동시성 테스트가 필요합니다.

## 16. 전체 서비스 요청 흐름 이해

대여 요청은 `브라우저 POST → 출처 검사·세션 쿠키 검증 → 인증 의존성 → 라우터 → 대여 서비스의 조건 검증 → 저장소 → ORM·DB 커밋 → 303 이동 → GET /app → 연관 데이터 조회 → Jinja2 HTML 응답` 순서입니다. 검증 실패 시 전역 예외 처리기가 상태 코드와 오류 화면 또는 JSON을 반환합니다.

## 17. 양방향 연관관계의 순환참조 문제 이해

`User.loans → Loan.user → User.loans`처럼 객체를 끝까지 JSON으로 바꾸면 무한 재귀나 지나치게 큰 응답이 생길 수 있습니다. 현재는 SSR 템플릿에서 필요한 속성만 읽어 전체 객체 그래프 직렬화를 하지 않습니다. JSON API로 확장한다면 대여 응답에 `id`, `status`, `book_id`, `user_id`처럼 필요한 필드만 지정한 DTO(응답 전용 모델)를 사용하고 역방향 관계는 생략합니다. 이 DTO는 현재 구현이 아닌 확장 전략입니다.

## 18. 세션과 JWT 인증 방식 비교

| 비교 | 일반적인 서버 저장형 세션 | 서명형 JWT |
| --- | --- | --- |
| 동작 | 서버에 로그인 기록을 저장하고 전달받은 세션 ID로 조회 | 토큰에 사용자 식별 정보·만료 시간을 담고 서명과 필요한 조건을 검증 |
| 장점 | 서버 기록 삭제로 즉시 인증 취소하기 쉬움 | 여러 서비스가 공유 세션 저장소 조회 없이 인증 정보를 검증하기 편함 |
| 단점 | 세션 저장소가 필요하고 서버 여러 대에서 공유해야 함 | 즉시 취소·권한 변경 반영에는 추가 설계가 필요하고 갱신·키 관리가 복잡해짐 |
| 적용 조건 | 브라우저 중심 서비스, 즉시 인증 취소가 중요한 경우 | 모바일·외부 API나 여러 서비스에서 인증 정보를 공유하는 경우 |

둘 다 탈취 방지에 HTTPS와 안전한 보관·만료 정책이 필요합니다. JWT도 쿠키에 저장할 수 있으며, 쿠키 자동 전송에는 CSRF 방어가 필요하고 자바스크립트가 읽을 수 있는 저장소에는 XSS로 인한 탈취 위험을 고려해야 합니다. [OWASP 설명](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)

이 프로젝트는 **Starlette의 서명 쿠키 세션**을 선택했습니다. Jinja2 페이지·폼 중심이라 브라우저의 쿠키 자동 전송을 활용하고 별도 JWT 발급·갱신 흐름을 줄일 수 있기 때문입니다. 서버에 별도 세션 목록을 저장하는 방식은 아니며, 서명은 위조를 막지만 쿠키 내용을 암호화하지는 않습니다. `HttpOnly`, `SameSite=Lax`, 운영 HTTPS 전용 쿠키를 사용하며, 로그아웃은 현재 브라우저 쿠키를 제거하지만 복사된 쿠키를 개별적으로 즉시 폐기하는 기능은 없습니다. [Starlette 설명](https://starlette.dev/middleware/#sessionmiddleware)
